### Authority: commit launch inputs before spawn

The schema and source transaction wiring now support exactly one prepared-launch transition for V2. Operational V2 admission/history are still closed; pure JSON journal validation is not issuance or receipt acceptance:

```text
started(admission)
  -> launch_prepared(id, launch)
  -> finished(id, receipt)
```

`launch` is a closed record containing:

```text
version: 1
historyDigest                 # journal prefix before this transition
configurationSha256           # raw native-config.json bytes
runtimeRequirementSha256      # raw fixed sibling bytes
invocationDigest              # canonical exact parent invocation
scopedAuthIdentityDigest      # observed identity only; never credentials
implementationDigest          # frozen selection, including evaluator/auditor
supervisorPid
```

Rules:

1. Only the owning pending admission can prepare once. The pre-spawn record is durable before the driver is allowed to spawn. It cannot be supplied by the producer, reconstructed after execution or reissued on resume.
2. The preparation transaction owns the existing short origin scope. It validates/writes configuration with the genuine original lease, rechecks deadlines/origin/lease, appends the launch record in that same transaction, then releases the lock before execution. Do not nest a second ledger transaction inside `withAdmissionOrigin()`.
3. Configuration's history binding refers to the prefix **before** `launch_prepared`; resume rederives that prefix, not the entire later journal. This avoids circular hashes and post-hoc rebasing.
4. Setup can fail before this transition; partial files remain evidence. Prepared-but-unfinished attempts remain interrupted/pending with unknown spend/time. No retry, orphan repair or synthetic zero settlement.
5. Hashes establish correlation against cooperative ledger state, not operator authentication or malicious same-user filesystem protection.

### Requests, continuation and meters

For each request, retain credential-free evidence sufficient to revalidate:

- the prepared logical instructions, tool schemas, user/task/history input and selected model/thinking/tier;
- the final materialized supported outbound representation after callbacks and transport framing;
- request/attempt/response identity, actual returned model metadata and explicit required usage/tier fields;
- exact tool-result content used in the next parent request, correlated to the recorded tool result and child run—not merely equal usage totals.

Current producer-side enforcement compares the canonical JavaScript JSON value of the full outgoing body with a process-local digest of the post-callback payload. Before callbacks, it snapshots the logical instructions/tool/input fields; callback mutation or replacement of those fields is rejected. HTTP requires an explicit string body in the snapshotted init object. WebSocket supports only `response.create` framing with that single top-level `type` removed; all other content must match. Request/Blob/stream bodies, cache-delta/other framing transformations and non-round-trippable UTF-8 are not silently accepted. The 1 MiB check applies after serialization, before parse/hash/send; it is not a bound on caller construction or serialization allocation.

### Native receipt and resume

Keep the existing four-field ordinary receipt for inert/v1 campaigns. V2 requires an additional `nativeAudit` field:

```text
nativeAudit: {
  version: 2,
  evidenceDomain,
  implementationDigest,
  launchDigest,
  evidenceDigest,
  supervisorPid,
  parentPid
} | null
```

`launchDigest` hashes the committed launch record. `implementationDigest` binds the frozen evaluator/auditor source selection; the explicit native audit version identifies its evidence contract. `evidenceDigest` covers a deterministic inventory of raw-byte hashes for the configuration, requirement, invocation, supervisor and all parent/child/native streams actually audited. - Fresh and historical acceptance call the same hard-wired auditor through the shared receipt route. Native policy is selected by trusted campaign expectations, never inferred from a producer flag or an optional file.
- Native loading enforces fixed paths, private ownership/permissions, regular single-link files, strict UTF-8, bounded sizes/counts/aggregate bytes and stable observations. Missing, duplicate, extra, aliased, truncated or incompatible evidence is rejected. Reuse bounded readers; do not create a parallel unbounded loader.
- The existing v1 cooperative native audit remains historical diagnostic validation only. A v2 native receipt cannot fall back to it. Reuse its algorithms behind the versioned native contract rather than accept v1 records by relabeling them.
- `nativeAudit: null` is permitted only for a failed, integrity-failed, unknown-cost settlement. It never certifies a completed native workflow or lets another trial advance. Failure before a result exists retains the existing sanitized failure-artifact behavior.
- Resume checks the concrete frozen implementation before interpreting evidence, derives the original launch-prefix expectations, reloads/re-audits evidence and compares the entire receipt before admission. It does not reopen old credentials, require an expired lease to become live, backfill records or reissue an origin.
- Human correctness judgment remains separate. A technically valid receipt does not replace pending blinded grading.
